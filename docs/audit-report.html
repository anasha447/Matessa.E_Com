Matessa platform — full-stack audit & hardening

One Spring Boot backend serves two independent storefronts: Matessa (yerba mate, India) and Adventure. This report explains how the system works, what the audit found, every fix that was made, and what was verified. Branch feat/store-isolation, November 2026.

Summary

Stores are separate

Every product, customer, admin, cart, order, coupon and analytics view lives in a per-store Postgres schema inside each service's database. Tokens, cookies, cache keys, images and Kafka messages are all tagged with their store and refused anywhere else. The gaps the audit found — a silent default store, a public gateway that let callers pick the store, dropped Kafka records — are closed.

Security

Three high findings fixed: production no longer marks unpaid card orders as paid, the login rate limit can't be bypassed with a forged IP header, and the browser proxy no longer exposes raw tokens or internal endpoints. Ten medium and six low findings fixed or explicitly deferred.

Checkout is correct under failure

Stock and coupon uses are reserved under an id, released on every failure path, and expired if the order never arrives. One idempotency key per checkout visit means double clicks, retries and reloads can't create a second order.

Ready to scale on a VPS

Any service can run as several replicas: outbox rows are claimed with SKIP LOCKED, scheduled jobs take a cluster lock, images live in a shared bucket. Caddy is the only thing facing the internet.

How the system works

  1. Browser → Caddy. TLS for MATESSA_DOMAIN and ADVENTURE_DOMAIN; Caddy overwrites X-Forwarded-For/X-Real-IP with the address it actually saw.
  2. Caddy → storefront (Next.js). Pages render server-side; the browser calls only same-origin routes. Sign-in tokens live in httpOnly cookies the browser's JavaScript can't read.
  3. BFF → gateway. /api/bff/* forwards only allow-listed areas, adds the store id (X-Tenant-ID, fixed in code), the bearer token from the cookie, and the client IP Caddy wrote. It refreshes an expired token once and retries.
  4. Gateway. Requires a known store, verifies the RS256 token (signature, issuer, expiry) and that it belongs to that store, rate-limits per store + client, then routes via Eureka with circuit breakers.
  5. Service. Re-checks store and token (defence in depth), sets the Postgres search_path to the store's schema, and does the work. Cross-service effects travel as Kafka events written through a transactional outbox.

Checkout: the saga

On the checkout page

The key is created once when the page loads and reused by every submit from that visit. Once a request has gone out with an unknown outcome, the key is locked: changing the basket then gets 422 IDEMPOTENCY_KEY_REUSED and a "check your orders" prompt instead of a possible duplicate. One request in flight, a 20-second timeout, a leave-page warning only while submitting, and success replaces history so Back can't resubmit.

Guards (Matessa)

Empty cart → /cart. The basket is re-priced on arrival; unavailable lines, over-stock or over-limit lines and price changes are listed with one "update my basket" button, and ordering is blocked until fixed. Indian mobile and PIN code are validated inline; the form survives a reload or a mid-checkout sign-in.

Stock model

Stock lives on variants — one stock path for cart, checkout and reservations. A product without variations gets one hidden default variant when it is created; that variant holds the product's own stock. Adding the first real variation (size/colour) retires it, and each variation carries its own stock; removing the last variation brings the default back at stock 0. Admins see it as "Product stock (no variations)", which can be edited but not deleted. Existing products without any variant received a default variant (stock 0) in migration V8.

What the live run found and fixed

FindingFix
A signed-in shopper retrying a checkout that had already succeeded (lost response) got "Cart is empty" instead of the order — the order had emptied the cart.The finished idempotency key is looked up before the cart; the same request returns the original order, a different one still gets 422. Regression test added.
The first checkout after a restart timed out reserving stock (3 s limit on a cold service); the release timed out too, so stock stayed held until the expiry job.Reserve/release get their own 8 s limit (CHECKOUT_RESERVE_TIMEOUT). The held stock was returned by the expiry job as designed — nothing was lost.

Also confirmed live: every placed order's stock reservation reached CONFIRMED through Kafka; an empty-cart visit to /checkout redirects to /cart; both storefronts build and render with no app console errors.
